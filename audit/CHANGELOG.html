阶段四十 · 修复「返回」崩溃（画廊后退空 self.image）

2026-08-16

动机

真机（KPW3）点击画廊底部「返回」按钮导致 KOReader 整体崩溃。设备 crash.log 栈回溯定位：frontend/ui/widget/imagewidget.lua:264: cannot render image → 经 CenterContainer/FrameContainer/OverlapGroup/VerticalGroup → main.lua:1584 查看器 paintTo → uimanager.lua:1279 _repaint ← handleInput（来自「返回」点按）。即点按触发重绘时，单图 ImageWidget 拿到 nil 图像而报错。

根因

画廊态不构建主图 widget，self.image 可能为 nil。两种触发路径：① 书签段退回画廊（_exitBookmarkView 置 self.image = nil 后 _enterGallery）；② 阅读视图直接进画廊、尚未加载单图。原 _exitGallery 的 else self:update() 分支在 self.image == nil 时直接重建单图 widget，_new_image_wg() 以 image = nil 建 ImageWidget，重绘即崩。此为「书签入画廊」（阶段三八）新功能引入的回归。

具体改动点

文件性质改动说明
main.lua · ArtGalleryViewer:_exitGallery 修 改为：若 self.image 有效且目标索引 == 当前索引 → 直接 update()（无切换闪烁）；否则（含 self.image == nil 的书签画廊/直进画廊路径）→ 改走 switchToImageNum(target)，由它按当前索引先把图片加载回 self.image 再 update()，确保单图 widget 拿到有效图像，杜绝 cannot render image 崩溃。仅修正取图时序，无其它行为变化。

校验

✓ LuaJIT 语法校验：SYNTAX OK（main.lua） ✓ 工作副本 ≡ 干净副本（diff -q IDENTICAL） ⚠ 真机复测待用户授权部署后执行（HITL）：书签画廊/直进画廊点「返回」不再崩溃，且正确回到对应单图 ✓ 版本号维持 v1.0.20 未升版；未发 Release（依「发版须经同意」纪律）

阶段四一 · 修复「返回」无反应（空主池 + 删除唯书签边界）

2026-08-17

动机

真机（KPW3）复测：图库中仅有「一张书签」时删除该书签，再点底部「返回」按钮——无崩溃，但**无任何反应**（画廊卡住，无法退出）。

根因

画廊缩略图数据来自 self:_tabList()（按当前段过滤），不重设 self._images_list / self._images_list_nb——后者始终是主图池计数。当用户处于「无当前单图」路径（书签段退回画廊后 self.image == nil），_exitGallery 走 else 分支调 switchToImageNum(target)。而 switchToImageNum（main.lua:3826）开头有硬守卫：if ... or image_num > self._images_list_nb then return end。

边界触发：整本书无常规图片、唯一可看内容就是那张书签时，主池 self._images_list_nb == 0。删除唯书签后点「返回」：target(=1) > _images_list_nb(=0) → 守卫**静默 return**（无切视图、无崩）→ 表现为「返回无反应」。此为「书签入画廊」（阶段三八）+ 阶段四十取图时序调整的边界交互回归。

具体改动点

文件性质改动说明
main.lua · ArtGalleryViewer:_exitGallery 修 在 else 分支：先判 (self._images_list_nb or 0) < 1——主池已空（唯一内容即刚删掉的书签）时，直接 self:onClose() 关闭查看器回阅读页（与 _ignoreImage 在 nb<1 时 onClose 的既有先例一致），避免 switchToImageNum 静默 no-op；否则对 target 做 math.min/max 范围夹紧后再 switchToImageNum(target)，杜绝越界静默失败。

校验

✓ LuaJIT 语法校验：SYNTAX OK（main.lua） ✓ 工作副本 ≡ 干净副本（diff -q IDENTICAL） ⚠ 真机复测待用户授权部署后执行（HITL）：无常规图片、仅一张书签的书，删除该书签后点「返回」应顺利关闭查看器回阅读页（不再无反应、不崩） ✓ 版本号维持 v1.0.20 未升版；未发 Release（依「发版须经同意」纪律）

阶段四四 · 吸收 Glimpse v1.3.0 弹出菜单自动旋转修复（PopupMenu:onSetRotationMode）

2026-08-18

动机

用户吸收项③。弹出菜单（长按图片菜单 / ⋯ 菜单 / 忽略菜单）开启时，G 传感器的 SetRotationMode 事件只派发给最顶层 widget（即菜单本身），其下方的查看器收不到 → 自动旋转被静默阻断。对齐 Glimpse v1.3.0 的修复（官方 release note：「Auto-rotation works even with the ⋯ menu open」）。

根因

ArtGalleryPopupMenu 此前没有 onSetRotationMode 处理器；旋转事件被它作为最顶层 widget 接收却不处理，查看器永远收不到，表现为「菜单开着时转不动屏幕」。

具体改动点

文件性质改动说明
main.lua · 新增 ArtGalleryPopupMenu:onSetRotationMode(rotation) 增 当 self.on_rotate 已设、rotation 有效且与当前方向不同 → self:dismiss() 关菜单并调用 self.on_rotate(rotation) 把旋转交还查看器重排，return true。对齐 Glimpse v1.3.0 的 PopupMenu:onSetRotationMode。
main.lua · 三处弹出菜单注入 on_rotate 改 长按图片菜单（~2707）、忽略菜单（~2794）、⋯ 菜单（~3310）均注入 on_rotate = function(rotation) self:onSetRotationMode(rotation) end（self 为查看器）。旋转时菜单关闭、查看器按新方向重排并重新打开（zoom/pan 持久化保留视图）。未注入 on_rotate 的弹出菜单（如有）旋转时保持旧行为，无回归。

现状核实

当前扫描器支持 CBZ / PDF / DJVU（按文件内嵌图片记录抽取）。.MOBI 是单文档流式格式：crengine 把全书渲染成文字页，内嵌图片混在 HTML 流中，KOReader 的 crengine Document 提供 getPageCount/getPageText，但没有「枚举全书图片」的公开 API。漫画类 MOBI 通常是整页即一张图（图片版漫画），文字极少；其图片以独立图片记录（Palm DB record / KF8 resource）存于 MOBI 容器内。

三套可行方案

方案思路优点缺点 / 风险
A. 解析 MOBI 容器抽图（推荐）纯 Lua 解析 MOBI 头（Palm DB header → rec0 解压 → MOBI header → 图片 record 偏移表），逐个读图片 record 解码为位图；复用现有扫描器「图片列表」结构与 .sdr 侧边缓存。与 CBZ 路径一致、离线、快；天然兼容「按书清缓存」「全书搜索记忆」。需手写 MOBI 解析（Palm DB / HUFF-CDIC 解压、KF8 资源分段），工作量中等；加密/DRM MOBI 不可解；图片可能经压缩需 mupdf 既有能力辅助。
B. 逐页渲染 crengine 页面位图把每页渲染成位图当「图片」，viewer 直接翻页。几乎零解析、复用 KOReader 自身渲染。文字书每页都是文字位图、无意义；漫画书每页=一张图尚可，但缩放/旋转/选图逻辑要重写；体积大、缓存贵。
C. 复用「外部画廊」入口把 MOBI 当图片存档用 showCbz 同类逻辑，但需先解出图片——仍回到方案 A 的解包。入口复用。仅是方案 A 的包装，无独立价值。

  • 推荐方案 A：解析容器抽图 + 仅对「图片型 MOBI」（全书图片数 ≥ 阈值且文字极少）启用，避免文字书误触发。

  • 兼容：与现有「按书清缓存」「全书搜索记忆」天然兼容（都按 doc_settings / .sdr）。

技术要点（为何这样实现）

KOReader 分页文档的阅读进度存于 doc_settings 的 last_page，由 ReaderPaging:onSaveSettings 在关书时据 live view.current_page 写出。因此只写 last_page 不够——关书会被 live 旧位置覆盖。正确做法是真正翻动 live 阅读位置：调用 self.ui.paging:onGotoPage(target)（KOReader 核心模块同源用法），它发 PageUpdate 事件 → ReaderView:onPageUpdate 更新 self.state.page 并重算，且会触发 checkAutoSaveSettings() 自动落盘；关书时 onSaveSettings 再据新 live 位置写 last_page，进度才真正持久化。
漫画（CBZ）每张图对应一页：扫描器 spine_index 即页码，故 target = meta.spine_index。仅对分页文档（CBZ/DjVu/PDF）生效；滚动文档（EPUB）图片散布、无稳定阅读顺序，乱跳进度反而误导，故跳过（self.ui.rolling 守卫）。并只在「更靠后」时推进（target > cur），回看早图不把进度倒退。

触发：用户要求参考 poker24.koplugin 的「游戏规则」说明弹窗（大面积纯文本，同为 TextViewer）实现，与 artgallery 修复后的「关于 美术馆」弹窗作比对，取更合适的写法。经实测对比两处源码得出结论：两套写法各自适配自身栈场景——poker24 经由自建 ButtonDialog 菜单（modal）主动 close 后同步 show、且下层 GameUI 为按钮驱动不持续刷新，故无需延迟；artgallery 经由读者主菜单 TouchMenu（callback 后才 closeMenu + 关闭动画整屏重绘），且下层 ArtGalleryViewer 为非 modal 的全屏图片查看器、交互会刷新自身，故必须保留 closeMenu + scheduleIn(0.3) + modal + close_callback（照搬 poker24 同步写法会退回 v1.0.8「无弹窗」）。两者共同精髓（先关菜单 + modal）artgallery 已吸收。唯一值得借鉴 poker24 的是其 show_menu = false：关于说明为纯只读文档，顶部再挂 ⋯ 菜单（复制 / 搜索）多余，且 poker24 注释指出 TextViewer 内部菜单（ButtonDialog）若 modal 处理不当会被遮蔽——show_menu=false 从根上消除这层冗余与隐患。

关于弹窗加 show_menu = false

  • 修在「关于 美术馆」回调的 TextViewer 中，于 modal = true 之后新增 show_menu = false（main.lua:5898 附近）。弹窗顶部不再显示 ⋯ 菜单图标，仅保留标题栏与关闭，UI 更干净；同时消除 TextViewer 内部菜单潜在的遮蔽风险。延迟（scheduleIn 0.3）与 close_callback 恢复 viewer 刷新均保持不变。
  • 核比对要点：poker24 showRules()（poker24ui.lua:2297-2395）使用 TextViewer:new{ ..., modal=true, show_menu=false } 且同步显示无延迟；artgallery 关于回调（main.lua:5849-5913）使用 closeMenu() + scheduleIn(0.3) + modal=true + close_callback。机理差异源于触发栈与下层组件刷新行为不同，不能简单说谁更优，但 show_menu=false 这一项明确值得采纳。
