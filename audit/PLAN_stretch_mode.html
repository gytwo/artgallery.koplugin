全屏「拉伸」模式 · 设计方案

仅方案 · 待审阅不落地实现 artgallery.koplugin（KPW3 / KOReader）

缘起：用户要求探索全屏态下新可选模式「拉伸」——按当前检测到的屏幕长宽，独立改变图片的宽/高比例以刚好填满整屏，相比现有全屏模式，不会因图片超高或超宽而损失可读内容。
本文基于已读真实源码（插件工作副本 + KOReader 纯净源码 koreader-kindle-v2026.07.1）撰写，所有行号锚点均经 grep 核验。本方案已于 2026-08-10 落地实现（见 CHANGELOG 阶段十五），下文保留原设计论证供追溯；实现与原文方案一致，仅"导航栏三态按钮 + 长按设默认"为审阅后新增的明确需求。

一、背景与动机

现有全屏填充仅两种态，由布尔开关 self._contain_in_fullscreen 控制（main.lua:983-993 _toggleFillMode）：

现有模式渲染数学表现代价
铺满（cover）
_contain_in_fullscreen = false（默认）		 scale = max(w_s, h_s) 图片占满整屏、无黑边 超高图裁上下 / 超宽图裁左右 → 边缘可读内容被切掉
适配（contain）
_contain_in_fullscreen = true		 scale = min(w_s, h_s) 整图完整可见、不裁切 超高图留上下黑边 / 超宽图留左右黑边 → 屏幕利用率低
屏幕 竖
超宽图
cover→裁左右
contain→留黑边
超高图
cover→裁上下
contain→留黑边
两种现有模式都无法「既填满整屏、又不裁切、还不留黑边」

拉伸（stretch）目标：取 w_scale 作用于宽、h_scale 作用于高（非均匀缩放），使图片按屏幕长宽比被变形后刚好填满整屏——不裁切、不留黑边，全部像素可见。代价是图片形变（圆形变椭圆、人物变胖/瘦），由用户主动选择。

二、现有机制核查（已读源码，确保方案可行）

2.1 填充比例的计算入口

_computeFitScaleFactor()（main.lua:3040-3068）按当前态返回统一 fit 比例：

  • cover return math.max(w_scale, h_scale)（取大 → 溢出裁切）
  • contain return math.min(w_scale, h_scale)（取小 → 留黑边）

2.2 图片控件的实际构造

_new_image_wg()（main.lua:1798-1822）在构建 ImageWidget 时传入：

  • scale_factor = wg_scale（fit 比例或 zoom 比例，0 表示适配态）
  • width = max_image_w、height = max_image_h（内容区尺寸）

2.3 关键可行性支点：ImageWidget 的非均匀拉伸路径

查纯净源码 frontend/ui/widget/imagewidget.lua：当 scale_factor == nil 且传入的 width/height 与位图自身尺寸不同时，渲染走 RenderImage:scaleBlitBuffer(self._bb, self.width, self.height, ...)（imagewidget.lua:332-336）——按 width×height 精确做非均匀缩放。 这正是「拉伸」模式可直接借力的落地支点，无需改 KOReader 源码（仅改插件传参）。

三、方案设计

3.1 状态模型：布尔 → 三态枚举

把布尔 _contain_in_fullscreen 升级为三态枚举：

-- 旧（二态）
self._contain_in_fullscreen = false   -- false=cover, true=contain

-- 新（三态）
self._fill_mode = "cover"   -- "cover" | "contain" | "stretch"

保留向后兼容：首次读取旧键 artgallery_contain_in_fullscreen 仍可映射到 cover/contain；新键 artgallery_fill_mode 带插件前缀持久化。

3.2 切换入口：循环三态

_toggleFillMode()（main.lua:983）改为循环：cover → contain → stretch → cover。按钮图标/文案随态刷新（现有 ⤢ 旁「全屏铺满屏幕」菜单项改文案显示当前态，如「全屏：铺满 / 适配 / 拉伸」）。

3.3 落地渲染（核心改动）

在 _new_image_wg() 构建 ImageWidget 处分支：

if self._fill_mode == "stretch" then
    -- 非均匀拉伸：令 ImageWidget 走 scale_factor=nil + 精确 width/height
    -- 触发 RenderImage:scaleBlitBuffer(bb, w, h) 填满内容区
    wg_scale = nil
else
    wg_scale = (self.scale_factor == 0) and self:_computeFitScaleFactor() or self.scale_factor
end
self._image_wg = ImageWidget:new{
    image = src, width = max_image_w, height = max_image_h,
    scale_factor = wg_scale,   -- stretch 时传 nil → 非均匀铺满
    rotation_angle = self._cur_rotation or 0,
    ...
}

cover / contain 两态沿用现有逻辑，行为不变。

3.4 fit 比例计算的配合

stretch 态下 _computeFitScaleFactor 不应再返回统一比例（会与 nil 传参语义冲突）。建议在函数顶部：if self._fill_mode == "stretch" then return nil end，由 _new_image_wg 的 nil 分支接管拉伸。其余两态逻辑不动。

3.5 缩放 / 双击 / 平移交互（关键抉择点）

stretch 态图片已被非均匀拉伸铺满整屏，无留白可平移；若再允许双击放大 / 捏合缩放（叠加均匀 scale_factor），会重新引入留黑边或裁切，违背「刚好填满」初衷。
推荐：stretch 态锁定 fit —— 禁用双击放大与捏合缩放（_applyNewScaleFactor 在 stretch 态直接 return，双击改走「切下一模式」或仅切换 fit/非 fit）。这保持语义干净、实现最简。
备选：允许在拉伸基础上叠加均匀 zoom（用户可放大看局部，但边缘会重新留黑边）——更复杂，且偏离用户「填满不损失内容」的诉求，不推荐。

3.6 旋转 / 智能选向

  • _smartRotation()（main.lua:3074）：stretch 态下选向无意义（反正会被拉伸填满），建议跳过自动旋转；
  • 用户手动旋转仍可叠加（先旋转再非均匀拉伸），由 _setRotation 记忆，不变。

四、KPW3 内存 / 续航 / 刷新影响评估（方案层）

维度评估结论
内存复用现有解码位图，仅渲染期多一次 scaleBlitBuffer 到精确尺寸（一次性，等同现有 cover 解码成本）；不新增常驻缓存无新增峰值
续航纯事件驱动；仅切模式/切图时一次解码+拉伸，无轮询、无后台 timer、无网络几乎无影响
刷新同 cover/contain：切图区域级 GC16 清残影 + 缩放/平移 flashless fast克制
可读性代价stretch 使图片形变（人物变胖瘦、圆变椭圆），属用户主动选择须 UI 明示「拉伸会变形」并提供一键回切

五、风险与待决项（提交审阅确认）

  • R1 缓存 key 稳定性：ImageWidget 在 scale_factor==nil 时用 width/height 参与缓存 hash（imagewidget.lua:139-145）。不同 width/height 生成不同 key，正常；但旋转态宽高互换会命中不同缓存，属预期。
  • R2 与缩放状态机的交互：_refreshScaleFactor(3084) / _applyNewScaleFactor(3109) 依赖 scale_factor。stretch 态 viewer 侧 scale_factor 仍应保持 0（逻辑"适配态"，驱动圆点 pill / 导航 / 双击），但 widget 侧传 nil——需保证状态机在 stretch 态不走 zoom 分支（建议 3.5 锁定）。
  • R3 与 HiRes 解码路径交互：_getHiRes(1834) 在 zoom>1 时换入全分辨率解码。stretch 态锁定 fit 后不应触发放大，故不走了；若未来允许备选缩放则需重算 ratio。
  • R4 抽屉态不受影响：抽屉态恒 contain（小屏不裁切），stretch 仅对全屏态生效，与现有 if self._fullscreen then ... 分支一致。
